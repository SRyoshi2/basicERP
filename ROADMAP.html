Aktuelles System

Installation und Selbsttest unter Windows

  1. Docker Desktop starten. In den Einstellungen müssen Linux-Container aktiv sein. Warten, bis „Docker Engine running“ angezeigt wird.
  2. PowerShell im Projektordner öffnen und den Installer starten:
    powershell -ExecutionPolicy Bypass -File .\scripts\install-windows.ps1
  3. Fragen beantworten. Für den lokalen Test sind localhost, Port 8080, Projektname basicerp und kein externer HTTPS-Proxy passend.
  4. Anwendung öffnen: http://localhost:8080/. Mit admin / admin anmelden.
  5. Passwort sofort ändern. basicERP sperrt das Dashboard bis ein neues, ausreichend starkes Passwort gespeichert wurde.
  6. Firmendaten prüfen: Im Dashboard „Firma“ öffnen, als Administrator Testdaten speichern und optional ein PNG-/JPEG-/WebP-Logo bis 2 MB hochladen.
  7. CRM prüfen: Im Dashboard „CRM“ öffnen, eine Firma oder Person mit Adresse anlegen, danach über Name oder Kundennummer suchen und erneut bearbeiten.
  8. CSV-Import prüfen: Unter „CRM“ auf „CSV importieren“ klicken. Eine UTF-8-Datei mit den Spalten Typ;Firmenname;Vorname;Nachname;E-Mail;Telefon;Straße;PLZ;Ort;Land auswählen, die Vorschau kontrollieren und erst danach übernehmen.
  9. Timeline prüfen: Einen bestehenden Kontakt zur Bearbeitung öffnen. Unterhalb der Stammdaten eine Notiz, einen Anruf, eine E-Mail oder einen Termin erfassen und anschließend bearbeiten. Administratoren können Einträge archivieren.
  10. Katalog prüfen: Im Dashboard „Katalog“ öffnen, eine Leistung mit Einheit, Steuersatz und Nettopreis anlegen. Einen Folgepreis mit nicht überlappendem Gültigkeitszeitraum ergänzen und den Eintrag über die Suche wiederfinden.
  11. Projektstamm prüfen: Im Dashboard „Projekte“ öffnen, ein Projekt mit dem vorhandenen Kunden, Status, Zeitraum sowie Geld-/Stundenbudget anlegen. Erwartet wird eine Projektnummer ab P-01001. Danach über Kunde oder Projektname suchen, den Status ändern und erneut öffnen.
  12. Arbeitspakete prüfen: Das Projekt öffnen und unter „Arbeitspakete & Controlling“ zwei Pakete anlegen. Planstunden, Mitarbeiter und bei einem Paket einen abweichenden Satz hinterlegen. Zwischen Board und Liste wechseln und einen Status direkt im Board ändern. Planstunden, Planwert, Restbudgets und Fortschritt müssen unmittelbar aktualisiert werden.
  13. Zeiterfassung prüfen: Im Dashboard „Zeiterfassung“ öffnen, Projekt und Arbeitspaket wählen, Datum, Stunden und Beschreibung eintragen und speichern. Zwischen Vorwoche, aktueller Woche und Folgewoche wechseln; die Tagessumme, Wochenstunden und abrechenbaren Stunden müssen stimmen. Den Eintrag öffnen, ändern und wieder speichern.
  14. Leistungserfassung prüfen: Im Dashboard „Leistungen“ öffnen, eine Katalogleistung, Projekt, Arbeitspaket, Leistungsdatum und Menge wählen. Nach dem Speichern müssen Menge × Preis und der abrechenbare Wochenwert erscheinen. Für das gewählte Datum muss ein gültiger Katalogpreis vorhanden sein.
  15. Ist-Controlling prüfen: Das verwendete Projekt erneut öffnen. Unter „Ist aus Zeit & Leistung“ müssen Ist-Stunden, abrechenbare und noch offene Stunden, Leistungswert, gesamter Ist-Wert und das verbleibende Betragsbudget unmittelbar zur Erfassung passen.
  16. Abwesenheiten prüfen: Im Dashboard „Abwesenheiten“ öffnen, den Jahresanspruch als Administrator setzen und einen Urlaubsantrag anlegen. Unter „Offene Genehmigungen“ genehmigen oder ablehnen. Das Urlaubskonto muss beantragte, genehmigte und verbleibende Tage korrekt zeigen; Krankheit darf den Resturlaub nicht reduzieren.
  17. Auswertung prüfen: Im Dashboard „Auswertung“ öffnen, einen Zeitraum sowie optional Projekt und Mitarbeiter wählen. Arbeitszeit, Zeitwert, Leistungswert und Gesamtwert müssen zu den zuvor erfassten Daten passen. „CSV für Excel exportieren“ lädt eine UTF-8-Datei mit Semikolon-Trennung und deutschen Dezimalzahlen; Mitarbeiter sehen ausschließlich eigene Daten.
  18. Ausgangsbeleg prüfen: Im Dashboard „Ausgangsbelege“ öffnen und einen Rechnungsentwurf mit Kunde, optionalem Projekt sowie mindestens zwei Positionen anlegen, beispielsweise 100,00 € zu 19 % und 50,00 € zu 7 %. Erwartet werden 150,00 € netto, 22,50 € Steuer und 172,50 € brutto. Belegart oder Position ändern und erneut speichern; die Version und Summen müssen aktualisiert werden. Ein Entwurf hat noch keine Belegnummer. Optional einen Kleinunternehmer-Entwurf mit 0 % und begründendem Hinweis prüfen.
  19. E-Rechnungseingang prüfen: Im Dashboard „Rechnungseingang“ öffnen und docs/examples/incoming-invoice-ubl.xml hochladen. Erwartet werden „Basisprüfung bestanden“, Rechnungsnummer BEISPIEL-2026-001, Verkäufer und Zahlbetrag. Das heruntergeladene Original muss bytegleich sein. Derselbe erneute Upload erzeugt keinen zweiten Eintrag.
  20. Normale Rechnung prüfen: Im Rechnungseingang „Normale PDF-Rechnung“ wählen, eine PDF auswählen und Rechnungsnummer, Datum, Verkäufer, Käufer, Betrag und Währung eintragen. Nach dem Speichern erscheint der Beleg als „Vollständig erfasst“; der Hinweis grenzt die manuelle Erfassung klar von einer inhaltlichen Prüfung ab.
  21. Systemprüfungen durchführen: Dashboard sichtbar, Readiness liefert {"status":"ready"}, API-Doku öffnet, alle Container sind healthy/running.

Server oder Arbeitsplatz

Installation und Selbsttest unter Ubuntu

Voraussetzungen: Docker Engine, Compose-Plugin, OpenSSL und curl. Der Benutzer muss Docker verwenden dürfen. Danach:

chmod +x ./scripts/install-ubuntu.sh
./scripts/install-ubuntu.sh

Nicht-interaktive Beispielinstallation:

./scripts/install-ubuntu.sh \
  --domain erp.example.de \
  --http-port 8080 \
  --project-name basicerp \
  --behind-https-proxy \
  --non-interactive

Bei --behind-https-proxy terminiert ein externer Reverse Proxy TLS und leitet intern auf den gewählten HTTP-Port weiter. Das Skript beschafft bewusst noch kein Zertifikat.

docker compose ps
curl --fail http://localhost:8080/api/v1/health/ready/
docker compose logs --tail 100

Backup und Restore:

./scripts/backup-ubuntu.sh
./scripts/restore-ubuntu.sh --backup ./backups/basicerp-YYYYMMDD-HHMMSS

Was macht der Installer?

Er validiert Docker, fragt Domain/Port/Projektname ab, erzeugt zufällige Django- und Datenbank-Secrets in der nicht versionierten .env, baut Images, startet PostgreSQL/Redis, führt Migrationen aus, erstellt den Admin einmalig und startet alle Dienste.

Was passiert bei erneutem Start?

Ein bestehender Admin wird nicht zurückgesetzt. Eine vorhandene .env wird nur nach Bestätigung beziehungsweise mit -Force/--force überschrieben. Ein Überschreiben nach produktiver Nutzung ist nicht vorgesehen.

Wann brauche ich GitHub?

Für die lokale Umsetzung nicht. GitHub-Zugang wird erst benötigt, wenn ein Remote-Repository, Pull Requests oder GitHub Actions eingerichtet werden sollen. Dafür genügt später ein vom Projektinhaber angelegtes leeres Repository und eine sichere Anmeldung über GitHub CLI oder einen verbundenen GitHub-Connector; Zugangsdaten gehören nie in den Chat oder das Repository.
