Aktuelles System

Installation und Selbsttest unter Windows

  1. Docker Desktop starten. In den Einstellungen müssen Linux-Container aktiv sein. Warten, bis „Docker Engine running“ angezeigt wird.
  2. PowerShell im Projektordner öffnen und den Installer starten:
    powershell -ExecutionPolicy Bypass -File .\scripts\install-windows.ps1
  3. Fragen beantworten. Für den lokalen Test sind localhost, Port 8080, Projektname basicerp und kein externer HTTPS-Proxy passend.
  4. Anwendung öffnen: http://localhost:8080/. Mit admin / admin anmelden.
  5. Passwort sofort ändern. basicERP sperrt das Dashboard bis ein neues, ausreichend starkes Passwort gespeichert wurde.
  6. Vier Prüfungen durchführen: Dashboard sichtbar, Readiness liefert {"status":"ready"}, API-Doku öffnet, alle Container sind healthy/running.

1 · Container

docker compose ps

db, redis, web, worker und nginx sollen laufen; Healthchecks dürfen kurz „starting“ zeigen.

2 · Readiness

Invoke-RestMethod http://localhost:8080/api/v1/health/ready/

Erwartet: Status ready.

3 · Logs

docker compose logs --tail 100

Keine dauerhaften Tracebacks, Neustartschleifen oder Datenbankfehler.

Am 05.10.2026 auf dem aktuellen Windows-System erfolgreich getestet. Alle fünf Dienste laufen; db, redis, web und nginx melden healthy, der Celery-Worker ist mit zwei Prozessen verbunden.

Installation und Selbsttest unter Ubuntu

Voraussetzungen: Docker Engine, Compose-Plugin, OpenSSL und curl. Der Benutzer muss Docker verwenden dürfen. Danach:

chmod +x ./scripts/install-ubuntu.sh
./scripts/install-ubuntu.sh

Nicht-interaktive Beispielinstallation:

./scripts/install-ubuntu.sh \
  --domain erp.example.de \
  --http-port 8080 \
  --project-name basicerp \
  --behind-https-proxy \
  --non-interactive

Bei --behind-https-proxy terminiert ein externer Reverse Proxy TLS und leitet intern auf den gewählten HTTP-Port weiter. Das Skript beschafft bewusst noch kein Zertifikat.

docker compose ps
curl --fail http://localhost:8080/api/v1/health/ready/
docker compose logs --tail 100

ZweckBefehlHinweis

Stoppendocker compose stopDatenvolumes bleiben erhalten.
Startendocker compose up -dStartet vorhandene Installation.
Neubauendocker compose up -d --buildNach Quellcodeänderungen.
Django-Prüfungdocker compose run --rm web python manage.py checkPrüft die installierte Backend-Konfiguration.
Nicht unbedacht ausführen: docker compose down -v löscht die Docker-Volumes und damit Datenbank sowie Dateien. Für normale Stopps immer docker compose stop verwenden.
Was macht der Installer?

Er validiert Docker, fragt Domain/Port/Projektname ab, erzeugt zufällige Django- und Datenbank-Secrets in der nicht versionierten .env, baut Images, startet PostgreSQL/Redis, führt Migrationen aus, erstellt den Admin einmalig und startet alle Dienste.

Was passiert bei erneutem Start?

Ein bestehender Admin wird nicht zurückgesetzt. Eine vorhandene .env wird nur nach Bestätigung beziehungsweise mit -Force/--force überschrieben. Ein Überschreiben nach produktiver Nutzung ist nicht vorgesehen.

Wann brauche ich GitHub?

Für die lokale Umsetzung nicht. GitHub-Zugang wird erst benötigt, wenn ein Remote-Repository, Pull Requests oder GitHub Actions eingerichtet werden sollen. Dafür genügt später ein vom Projektinhaber angelegtes leeres Repository und eine sichere Anmeldung über GitHub CLI oder einen verbundenen GitHub-Connector; Zugangsdaten gehören nie in den Chat oder das Repository.
